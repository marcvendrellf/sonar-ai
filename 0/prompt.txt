okay this is a review about phase 1, evaluate the findings, whether they are correct or not, and fix them if necessary, Verdict
Phase 1 is in good shape and delivers what the plan asked for: pure Zod + inferred types, zero React/Next/network imports, a reusable evidence gate with a negative test, and one complete golden run. The module boundaries and tsconfig strictness (`noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`) are better than the spec required. The findings below are coherence gaps in the fixture and doc contracts — not schema bugs — but they matter because this package is declared the single source of truth and the golden state drives the Phase 3 stub-runner and Phase 5 JSON schemas.
Findings, most to least important
1. `riskChecks[].actionId` point at actions that exist nowhere in the state. In golden-state.ts:165-166 the checks reference `acn_nvda_v0` / `acn_sie_v0` (the pre-resize revision-0 proposal), but the only actions actually stored — in both `proposedActions` (:211-214) and `finalRecommendation.actions` (:183-186) — are `acn_*_final`. So a UI trying to link "Nvidia was resized 35%→30%" from a risk check back to its action resolves nothing. The evidence gate catches dangling evidenceIds, but nothing guards actionId, so this passes silently. It's baked into the receipt too (:314-316). Fix: either store the revision-0 recommendation/actions in the state so the checks resolve, or repoint the checks at the final action IDs. The narrative wants to show the resize, so keeping the v0 actions is the more faithful option.
2. The `maxTurnoverPerEvent` contract comment is ambiguous and, read plainly, contradicts the engine. mandate.ts:15-16 says "Maximum fraction of NAV that may turn over in response to one event" — which reads as gross traded notional (the fixture deploys €500 of €1,000 = 50%). But Phase 2's `checkTurnover` explicitly defines it as sell-side churn only (`sellNotional / nav`, all-cash deployment = 0 turnover). Both can't be the source of truth, and this package is supposed to be it. Tighten the doc comment here to state the precise definition (sell-notional / NAV) so the LLM generating structured output in Phase 5 doesn't compute it the naive way and hallucinate a breach.
3. The receipt's internal evidence integrity is neither collected nor tested. `collectReferencedEvidenceIds` (integrity.ts:21-46) walks the top-level state but never descends into `state.receipt`, which carries its own `evidence[]` (6 records, omitting `ev_market`) and its own claim/event references. It happens to be internally sound, but by manual care, not by the gate. Since the receipt is the durable artifact, add a `findDanglingEvidenceIdsInReceipt(receipt)` (or fold the receipt into the collector) and assert it in the integrity test.
Smaller notes

* Derived views can silently drift. `proposedActions`/`riskChecks` (analysis.ts:72-73) duplicate `finalRecommendation.actions` and `riskReport.checks`. Fine as a UI convenience, but nothing asserts they stay in sync — worth an orchestrator-level consistency check in a later phase (and a one-line comment here saying they're derived, not authoritative).
* The schema can't express the phase invariants the commit claims. "UserDecision required before mutation" is enforced only by the orchestrator; the schema lets `userDecision: null` coexist with a non-empty `appliedOrders`, and `phase: "complete"` with everything null. That's a deliberate progressive-enrichment design, but since the commit message states the invariant, consider a `.superRefine` or a documented invariant test so the guarantee lives with the contract.
* Turnover has no home in `RiskMetrics` (agents.ts:83-90) — volatility/beta/concentration/sectorExposure are surfaced, but a turnover breach can only cite a number from the check's `numbers` map, not from metrics. Minor, but a turnover field would make the metrics panel symmetric with the four limits.
* Nit: `ID_PREFIXES.stageOutput: "stg"` (ids.ts:33) is defined but unused — stage outputs use type-specific prefixes (`frp`, `mrp`…). Drop it or use it.
* Nit: commit message cites zod 4.4.3; package.json:17 pins `^4.1.5`. Harmless, just inconsistent provenance.

What's genuinely good
Evidence gate is pure, reusable, and has a real negative test (`structuredClone` + injected dangling id). Every timestamped fact carries a `live|historical|synthetic` label and graph edges require ≥1 evidence id — the core "no uncited claims" invariant is structural. Fixture IDs are consistent with `ID_PREFIXES` throughout. `Money`/`Ratio`/`Confidence` primitives keep the rest of the tree dependency-light, and splitting out `primitives.ts` + `integrity.ts` (beyond the spec) was the right call.
